# M4 引擎构建报告（TELE，2026-09-21）

> 阶段：M4（引擎构建）完成。前置：M3 已按用户裁决（1192 对象版）关单。
> 结论先行：**NInfer 三元引擎在本机（RTX 5080 / sm_120a）构建成功并验证通过——537/537 目标零错误，SASS 原生 sm_120a，k8v4 / dflash2 / vision 全参数实证可用。**

## 1. 构建链（全部实测落定）

| 组件 | 版本/位置 | 备注 |
|---|---|---|
| CUDA Toolkit | **13.3.1（nvcc V13.3.73）旁装 `J:\Bonsai\landing\cuda-13.3`** | CMakeLists 硬门 ≥13.1（CMakeLists.txt:L59-62）；本机原 nvcc 13.0.88 不过门 |
| MSVC | VS2022 Community cl 19.44（vcvars64） | 作者脚本 fallback #2 命中 |
| Ninja | 1.12.1（VS 自带） | `-G Ninja` |
| FFmpeg dev | BtbN master（FFmpeg 8.x，avcodec-63）shared 包 | 仓根 `ffmpeg\{include,lib,bin}`（见 §3） |
| 架构 | `CMAKE_CUDA_ARCHITECTURES=120a` + `NINFER_SM89=1` 定义 | 见 §4 关键发现 |

构建命令（cmd /c 包装 vcvars + VSLANG=1033）：
```
cmake -B _build_5080 -S . -G Ninja -DCMAKE_CUDA_ARCHITECTURES=120a -DCMAKE_BUILD_TYPE=Release -DCMAKE_CUDA_COMPILER=J:\Bonsai\landing\cuda-13.3\bin\nvcc.exe
cmake --build _build_5080 --config Release -j 16
```

产物：`_build_5080\{ninfer.exe, ninfer-serve.exe, ninfer-perplexity.exe}` 各 ~226 MB（内嵌 fatbin）+ ffmpeg DLL 7 个 + CUDA x64 DLL（按作者 build_v1.0.8.bat 的 runtime 布局，exe 与 DLL 同目录）。

## 2. CUDA 13.3.1 旁装过程（两处坑）

1. **网络安装器失败**：组件走明文 HTTP 下载经代理后哈希校验失败（0xe0e000af，重试 4 次全挂，[EVIDENCE] Log.7104setup.exe.log: "File is not digitally signed, falling back to check for hash"→异常）；关代理直连后大文件中途被掐。**改用离线完整包** `cuda_13.3.1_windows.exe`（2,531,940,368 B 精确匹配 + Authenticode 签名 Valid/NVIDIA Corporation），GUI 自定义安装：仅 CUDA 组件、路径 J 盘。
2. **系统 CUDA_PATH 副作用**：安装器自动把系统级 `CUDA_PATH` 从 v13.0 改指 `J:\Bonsai\landing\cuda-13.3`（NVIDIA 默认行为，非人工操作）。影响评估：torch/ComfyUI 零影响（自带运行时 DLL）；用户已表态以后也想用 13.3，维持现状。现有 v12.6/v12.8/v13.0 目录完好。
3. 驱动 616.92（RTX 5080），满足 CUDA 13.3 运行要求，无需动驱动、无需重启。

## 3. FFmpeg 缺件与守卫化处置

基线 repo 不带 `ffmpeg\`（作者本地树才有，build bat 依赖它；MSVC 分支硬编码 link avcodec/avformat/avutil/swscale/swresample）。处置：

- 从 BtbN 下载 FFmpeg 8.x shared 开发包（include/lib/bin 布置到仓根 `ffmpeg\`）。
- 同时对 CMakeLists 做了**存在性守卫**（而非删功能）：顶层 `if(MSVC)` 内加 `EXISTS ffmpeg/include` 判断、src 侧 `NINFER_BUILD_MEDIA_ACQUIRE AND TARGET PkgConfig::FFMPEG` 判断——FFMPEG 缺席时 `decode.cpp` 自动走源码原生 stub 路径（`#ifdef NINFER_HAVE_FFMPEG` 的 #else 分支），FFMPEG 到位自动恢复完整版，零二次修改。

## 4. 关键发现：基线是 4090/sm_89 移植树，120a 需要 SM89 定义

**现象**：120a 首编即撞 `src/core/device.h(29): #error "NInfer requires NINFER_SM86 or NINFER_SM89"`。

**定性**（T-CHECKPOINT 三问后处置）：基线仓 Ambolio/ninfer-4090-windows 是上游 120a 参考实现的 4090/sm_89 移植版（仓内 PORT_v1.0.5/6.md 印证），全树约 30 处 `#if defined(NINFER_SM89)` 变体门控，`kTargetSmCount = 128`（4090）。作者三元补丁与全部实测数据（62-64 t/s、MTP K=2 96.7-130.8 t/s、PPL 6.435）均产自该 89 基线。

**处置（改 CMakeLists 一行）**：`if(CMAKE_CUDA_ARCHITECTURES MATCHES "89")` → `"89|120a"`，即 120a 构建复用作者的 SM89 代码路径（capped shared-memory w8 变体、launch 几何按 128 SM），同时 nvcc 生成**原生 sm_120a SASS**。等价性论证：

1. `kTargetSmCount=128` 与 **5080 的 128 SM（GB203）完全一致**，"填满一个驻留波"的 launch 策略等价成立；
2. M0 已实证补丁无内联 PTX（`__CUDA_ARCH__` 零命中），kernel 全为标准 CUDA C++，sm_120a 指令集是 sm_89 超集；
3. k8v4/NVFP4 的 SM120 专属真 kernel 仅在 120a 构建编译（non-sm_120a 构建编的是 throw stub，[EVIDENCE] sm120_kv_stubs.cpp:L22）——本构建已实证编入（构建日志出现 `small_t_k8v4.cu.obj`）。

**验证**：改后 537/537 全绿；`cuobjdump -elf ninfer-perplexity.exe` 输出 `arch = sm_120a`；`ninfer-serve.exe` usage 实证 `--kv-dtype bf16|int8|fp8|nvfp4|k8v4|rk4v4|rk4v4-e8`、`--spec mtp|dflash|dflash2 --draft-tokens N`、`--vision`、`--host-kv-mib`、`--max-context` 全部在列。
