## 1. R1 架构改写工程量（sm_89 → sm_120a）——**同意，附两个补强**

CODE 判断（方案 §3.2）：mma.m16n8k16 / cp.async / warp shuffle 均为 sm_80+ 通用指令，预期=CMake 标志级 + 调优常数重校，且 M0 留了"绑定深度"验证门——**方向与依据我方独立认可**。

补强两点：
1. **绑定深度判据主观化问题**：M0 判据"能回答补丁对架构的绑定深度"不可机器判定。建议客观化：对 patches/ 全量 `grep -c "__CUDA_ARCH__|sm_89|89" `，逐处人工归类（arch 宏分支/内联 PTX/注释），输出清单才算过门。
2. **arch flag 细节**：上游用 `sm_120a`（family-conditional variant）。建议补丁线也先试 `120a` 与上游一致；NVCC 报不识别再降 `120`。另外 sm_89 编译产物（cubin）在 sm_120 上不可直接加载，仅 PTX 可 JIT——"改 flag 重编"不是可选项而是必须项，方案已含，确认无误。

架构差异补充核查（CODE 问"有没有被忽略的差异"）：cp.async 双缓冲、38144 B 静态 shared（远低于 sm_120 上限）、warp shuffle——均无 Blackwell 语义变化；SM 数 80→84 与寄存器预算微差只影响调优常数（论文 §4.7 的 CTA 数/K 分块需按 5080 重校），不影响正确性。**结论：R1 等级"中"合理，但正确性风险≈0，风险集中在性能重校。**

## 2. 显存外推——**反对原论证，结论需重算（本次评审最大抓漏）**

CODE §3.1 用"作者实测稳态占用 6-7 GB"推出"16 GB 余量充足"。**该数字物理上不可能**：制品权重本身 7.74 GB（方案 §3 自己引用了论文 8,306,927,628 B），总占用 6 GB 小于权重本身，矛盾。真实出处应是 CSDN 标题"6g 显存闪电侠"的营销口径（大概率指 GGUF 5.9 GB 或扣除了某些项），不能作为工程数据。

正确的账（TELE 独立推算）：
- 固定项：权重 7.74 GB + CUDA context/驱动 ~0.5-1 GB + MTP 状态与 workspace 若干
- 可变项：KV 池。上游 v1.2.0 机制为"启动时按权重后剩余显存自动定容（留 1 GiB headroom）"[独立知识，来源=上游 README；**v1.0.8 行为待 M0 核实**]——若 v1.0.8 同机制，则 16 GB 卡上占用会自动长到 14-15 GB（KV 池 ~6 GB），而非停在 6-7 GB
- 影响不是"跑不了"，而是：① 262K 满上下文在 16 GB 上不可达，预计 bf16 KV 约 90-100K token、fp8 KV 约 190-200K（按 16 全注意力层粗算，待实测）；② M5 判据"显存对照作者口径 6-7 GB 级"在 16 GB 卡上语义错误，应改为"分项账本：权重/ KV / 其他三行实测记录"
- 修正后结论不变：**可行，余量够用**——但论证链必须换掉，否则后续排查会被错误基线误导

## 4. 遗漏风险（引导词 R4）

- **R7（建议新增）代理/网络依赖**：Ambolio 基线在 GitHub（用户 FlClash 随时可能关闭，关闭后端口残留但拒绝转发）；HF 亦需代理。对策已存在：hf-mirror.com 实测可达（TELE 已成功抓取 GGUF README）；GitHub 代理关闭时按既有降级惯例（先探直连再报告用户），并应在 M0 就把基线 clone 到本地、此后不再依赖 GitHub。
- **CUDA 版本策略**（CODE M0 判据"nvcc ≥13.1"、装 13.4）：下限合理，**上不封顶有风险**——论文验证环境 13.3、上游验证 13.1，13.4 为最新 toolkit，对老内核代码的新警告/错误行为未知。建议：优先读 docs/01 拿作者指定版本；拿不到则装 13.3（作者验证值），13.4 不作首选。M0 判据改为"nvcc 版本 ∈ {docs/01 指定值，否则 13.3}"。
- **MSVC 14.44 vs 论文 14.51**：低风险（host compiler 差异通常无碍），不单列，记录在案即可。
- R5 CSDN 付费、R6 许可：✅ 无异议。

## 6. 第三条路（引导词 R6）——**无革命性第三条路，但建议一处结构升级**

评估过的候选：等作者 sm_120 版（被动，否）；上游 master 自写三元支持（=重做论文，否）；WSL2 跑上游跑官方 nvfp4（背离三元目标 + 16 GB 放不下 nvfp4，否）；**把路径 C 从"最终降级备选"升级为"M6 前置基线"**（建议采纳）：
- 理由：M6 的"达标"目前只能和论文 4080S 数字跨卡对比（带宽差 30%、SM 差、架构差），不是干净参照；同卡跑一次 fork llama.cpp（PQ2_0，官方预编译二进制，半天，7.2 GB 下载）即得**同卡分母**，NInfer 加速比可量化——这也是对"NInfer 相对 fork 值不值"这个核心问题的唯一直接回答
- 成本：半天 + 7.2 GB；与主线零耦合；顺带验证模型可用性（质量基线）
- 注意：必须用 PrismML fork 二进制——**stock llama.cpp/LM Studio 拒载三元格式，且主线加载 Q2_0 会无警告输出乱码**（HF README 原话，CODE 方案未提此坑，若将来真走降级路线必踩）
