## 1. PPL 链路攻坚（发布缺件第三例）

首跑即 `bad_alloc`（评分首窗口）。checkpoint 插桩逐级定位到 flush 内 workspace 分配：

- **根因**：`layouts_impl.h` 的 causal_score workspace plan 只分配 logits [248320×1024] BF16（508 MB）+ 小项，**漏算三元输出头的 Hadamard 旋转 scratch**（[5120×1024] BF16 ≈ 10.5 MB）。作者 linear.cpp:L161-168 自己写了警告（"Omitting these cases would make every ternary weight die here"），其树里 plan 有此 scratch，但 **plan 侧文件不在 changed-files 发布包**——继 numeric.py、_ternary_ref.py 后第三处发布缺件。
- **修复**（保留在树中）：`layouts_impl.h` causal_score plan 增加 `scratch(causal_score, ops::detail::ternary_rotation_workspace_bytes(TextConfig::hidden, kCausalScoreTile))`，附注释说明缘由。
- 修复后 PPL 链路一次跑通。

## 4. 显存账本（三场景实测，16GB 卡）

| 场景 | 总占用 | 构成 |
|---|---|---|
| PPL 评分（bf16，全程稳态） | **10.6-10.8 GB** | 权重 6.70 + logits 508M + 旋转/前向工作区 ~0.5G + KV 256M + GDN 状态 150M + staging/context ~0.7G |
| serve 生成（bf16，KV 8192） | runtime 982 MiB，free **6.98 GiB** | 引擎预算口径（含 CUDA graph） |
| serve 生成（**k8v4，262,144 满血**） | **15.36 GB**（余 ~900 MB） | KV 池 4096/4096 页 ≈ 6.0 GiB + 权重 6.70 + 运行时 |

上下文能力结论：bf16 纯显存 ~10 万 token；**k8v4 满血 262,144 实测通过**（贴天花板，启动前关其他 GPU 程序；OOM 则降 196608/131072）；`--host-kv-mib` 可继续向内存扩展；模型原生上限 262,144。
