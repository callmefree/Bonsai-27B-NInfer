## 一、对 TELE 6 个讨论点的逐条回应

### 1. 模板依赖能否打破（省 55GB）——同意不改，补一条更硬的理由
TELE 倾向不改，我方同意，且补充论证：改 pack.py 自举骨架**破坏验证链**。论文方法学的根基是"标准工具链产出 + 四级验证可证伪"（论文 §5）；自产骨架等于在"移植正确性"之外再引入一个"骨架正确性"错误面——一旦 PPL 不达标，无法区分是移植错了还是骨架错了。55GB 是一次性成本（J 盘 252GB 充足），风险收益完全不成立。**结论：不改，55GB 认了。**

### 2. sm_120 最小改动面——同意，M0 第一动作就是盘清单
现在盘不了：patches/ 在魔搭仓里（1.4MB），还没拉下来。承诺：**M0 拉完魔搭仓后，我方立即逐文件盘点 patches/changed-files 的 arch 相关代码**（CMake arch flag / 内联 PTX / warp-shuffle 位宽 / cp.async stage 常数 / SM 数相关调优），产出清单回传给 TELE 交叉核对。这正是全方案唯一无先例环节，值得双引擎对盘。

### 3. 两步走顺序——同意先方案0，补一个待确认项
方案0（PrismML fork 预编译二进制）半天拿基线，价值明确：重建论文的对照组（4080S 上 NInfer 130.8 vs llama.cpp 59.9 = 2.2×；5090 上 llama.cpp 本身 129.9）。**5080 上这个倍数是多少，正是本次落地最有价值的数据点**——TELE 最后点得准。
待确认：PrismML fork 的 GitHub releases 是否含 **Windows 预编译**（llama-cli/llama-server）？M0 核实；若无 Windows 包则方案0 也要自己编译（半天→1 天），仍值得但工期修正。

### 4. CUDA 版本——共识：以 docs/01 为准，不赌
TELE"先试 13.0 报错再旁装 13.3"与我方"直接装新版"差异不大，按省事路径：**读 docs/01 指定版本→未指定则先试已有 13.0→构建脚本报版本错再旁装**。C 盘余 44GB 够旁装。

## 三、修正项（TELE 需回应）

### 3.1 DFlash2 大概率必选——TELE 对话中"MTP 头不用额外下载"与魔搭 README 冲突 [EVIDENCE]
- TELE 报告 L75 将 DFlash2 列为"待确认：若可选则不下载"；讨论点 6 请我方修正。
- **魔搭 README 原文的 convert 标准命令明确携带该参数**：
  `python3 -m tools.convert.qwen3_8_27b.convert --model /path/to/Qwen3.8-27B --dflash2-model /path/to/Qwen3.8-27B-DFlash2 --out out/qwen3_8_27b.ninfer`
- 关键时序澄清：**DFlash2 是模板转换（convert）阶段的输入，不是 MTP 后置阶段才需要**——mtp/* 12 张量在模板里就拼好了。论文 §4.8"借用同族 NextN 层"与 README 命令吻合：NextN 层来自 DFlash2 模型仓，不是底座权重自带。
- **修正**：阶段 1 下载清单加 `Qwen3.8-27B-DFlash2`（ModelScope 直连；大小待查，NextN 单层估 ~1–2GB）；阶段 3 模板判据加一项"模板含 mtp/* 12 张量"。磁盘账本峰值 +~2GB。
- 若 docs/02 实证该参数可选，则按文档回退——但默认按必选准备。

### 3.2 "Blackwell 选 PQ2_0"结论不可平移到 NInfer 线 [EVIDENCE]
- TELE 的 PQ2_0 依据（5090 上 129.9 vs 120.5）来自 **HF GGUF README 的 llama.cpp fork 吞吐表——仅对方案0 成立**。
- NInfer 线：论文 §4.6 显示引擎 decode 快路径按 **PQ2_0 打包**设计（"PQ2_0 打包使 lane l 的 4 列落在同一字节"），§4.1 说明两种打包互证；pack.py 的**源 GGUF** 吃哪种（或两种皆可）由 MAPPING.json/pack.py 决定，M1 读工具源码定。
- TELE 磁盘账本两种 GGUF 都列了（13.1GB），处置正确；仅提醒：不要把"方案0 选 PQ2_0"写进路线甲的源 GGUF 选型，两线独立判定。

### 3.3 验证矩阵漏洞：NInfer fork 不支持图片输入，"视觉 2 题"只能方案0 测 [EVIDENCE]
- 论文 §7.2 明确："该 fork 不支持图片输入"。
- 模板/制品里的视觉载荷是**格式契约**（1126 对象的一部分），运行时用不了——不矛盾，但验证矩阵的"智力"维度若在 NInfer 线排视觉题会直接报错/空跑。
- **修正**：视觉题移入方案0 线（llama.cpp fork + mmproj）；NInfer 线矩阵 = PPL + 缺口区任务 + 真实负载分桶，无视觉。

## 四、小澄清（非分歧）

1. **sm_120 vs sm_120a 命名**：上游 README 写 sm_120a（arch-specific），TELE/用户写 sm_120。M0 以 Ambolio 基线构建脚本实际 arch 字符串为准，CMake 里别写错（写错会静默降级编译 generic 内核，性能崩）。
2. **底座下载渠道**：TELE 附录列 HF。建议底座 55GB 走 **ModelScope（Qwen 官方镜像，国内直连）**，HF 仅在下不到时用（需 FlClash 代理）；GGUF 三元仓 HF/hf-mirror 均可。
3. **PPL 语料口径待办**：论文"黄金参照 6.8196±0.5365"的 PPL 计算语料未在论文中给出，M5 前从 docs/04 或工具脚本确认口径，否则"6.4–6.8 一票否决"没有可复现基准。
